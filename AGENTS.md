# Repository Guidelines

## Project Structure & Module Organization
This repository is a full-stack SimplePoint dashboard project. Backend Java modules live at the root as `simplepoint-*` directories, including `simplepoint-api/src`, `simplepoint-core/src`, `simplepoint-boot`, and related support modules. The React frontend is isolated in `simplepoint-react`, a pnpm/Nx workspace with apps under `apps/*`, shared libraries under `libs/*`, and static/mock assets under `public/`. Documentation and operational notes are in `README.md`, `doc/`, `plugins/`, and module-level README files.

## Build, Test, and Development Commands
Use root Gradle commands for backend work:

```bash
./gradlew build
./gradlew test
```

Use frontend commands from `simplepoint-react`:

```bash
pnpm install
pnpm dev:host
pnpm build
pnpm typecheck
```

`pnpm dev:host` runs the host app locally. `pnpm build` builds the common package and host app through Nx. `pnpm typecheck` runs TypeScript checks for the common and host apps.

`-Psimplepoint.frontend.skip=true` is restricted to backend tests. Service distributions must run with frontend packaging enabled. `installDist`, `distZip`, and `distTar` depend on `verifyFrontendDistribution`, which checks the packaged entry and its declared JS/CSS assets. After deployment, verify the served federation manifests and entries as well as service health; a healthy Java service alone does not prove its UI is available.

## Coding Style & Naming Conventions
Java code should follow conventional package naming under each module's `src/main/java`, with classes in `PascalCase`, methods and fields in `camelCase`, and constants in `UPPER_SNAKE_CASE`. Keep service, controller, mapper, and model names explicit and domain-oriented.

Frontend code uses TypeScript and React. Prefer `PascalCase` for components, `camelCase` for functions/hooks, and colocate feature-specific files inside the owning app or library. Use 2-space indentation for TypeScript/TSX and keep shared logic in `libs/*` instead of duplicating it across apps.

## Mandatory Platform UI Standards
All new features and changes to existing features must use the platform UI component and interaction contracts wherever they cover the requirement. Do not use native Ant Design table, button, form, picker, or pagination components in business pages to recreate behavior already provided by a platform component.

- Use `SimpleTable` for resource CRUD list pages with a server `/schema`, server pagination and query contract, and permission-filtered buttons. Keep the list, filters, sorting, selection, refresh, and standard create/edit actions in its controller. Use `DataTable` for feature-specific, composite, or in-memory tables that do not have a resource CRUD contract; do not use raw Ant Design `Table` for these pages.
- Define resource CRUD actions in the server schema. For composite pages without that contract, derive action descriptors from server permissions or capabilities. Render list toolbar, record, and detail actions through `SimpleTable` or the shared `TableActions` renderer. Do not hand-code native Ant Design `Button` controls for actions that the platform action renderer supports. Keep action permission checks on the server.
- Use shared platform form and selection controls, such as `SForm` and `EntitySelect`, when their behavior matches the field. A native Ant Design control is allowed only when no platform component covers the interaction, such as a specialized editor or a dialog's confirmation controls. Document the reason in code when the exception is not obvious.
- When adding or reviewing a feature, check the existing platform components in `simplepoint-react/libs/components` first. Do not add a parallel local table, action toolbar, or selection implementation for behavior the platform already owns.
- Published form business pages must open directly on the standard resource list. Render the designed form inside the platform create/edit drawer; expose detail and approval/history through permission-derived list actions. Do not introduce top-level Form/Data/Submission tabs or a second CRUD controller. Detail tables must retain usable column widths and scroll within their own bounded width/height in editors and read-only views.

- Retained-page overlays must follow the owning page selection. Reads must be cancelled or fenced on close, owner change and authorization scope change; writes must use the shared operation lock. Prefer `loadEditingRecord` to reimplementing the standard edit lifecycle.
- Table appearance preferences must use the shared account-synchronized preference store, retaining local edits on synchronization failure and fencing stale loads. Automatic identities must use the retained page location, not the global pathname/hash of another tab.
- Render dates and timestamps through the shared temporal formatter using the platform locale. Calendar dates and civil times must retain their values; only offset-bearing instants are converted to the viewer timezone. Never change storage/query values for presentation.
- Domain modules own complete status labels and state transitions; use platform semantic status tones. Unknown or terminal statuses must not default to a running appearance.
- Public domain error envelopes must include a stable, namespaced `messageKey` with supported translations while preserving diagnostic codes. Do not translate by matching English exception messages or expose submitted values as translation parameters.
- Localized record values use `@LocalizedField`, the shared `LocalizedText` contract and the platform SForm editor; field-title translation keys remain separate. Persist translations inside the owning aggregate transaction and validate every locale/value on the server. Tenant overrides must never modify global platform message keys.
- Localized values inherit the source field's read/write policy across every language. Masked/hidden values must not trigger translation reads. Preserve platform inheritance keys and stable resource identities; apply tenant display overrides only to authorized projections. Nested translation drawers share the parent draft and save lifecycle, fence stale reads and restore their opening snapshot on cancel.
- After moving an approved native control, update its exact UI exception entry and run `node scripts/ui-standards/audit.mjs --strict` from the frontend workspace. A stale entry is a failed quality gate.

- Resource declarations must match the contexts that the domain actually supports. Do not register tenant-only functionality for PLATFORM/SYSTEM and compensate with an unavailable page; disabled placeholders must not be presented as usable menus. Keep server scope enforcement and resource declarations aligned. Home widgets and shortcuts must derive visibility from the same authorized routes or server capabilities.
- Workspace resources and package management are independent resource pages. Account/workspace settings reuse `SettingsLayout`; do not embed another set of business-list tabs inside settings. Owner-only capabilities remain server-derived.

## Mandatory Table and Form Extension Standards

- Standard table page sizes are 50/100/200/500, defaulting to 50. Browser table schemas and server execution limits must agree through `TablePagination`; preserve separately bounded lookup directories and transport cursors. Tables fill their bounded parent for loading, empty and populated states, with scrolling inside the body and pagination outside it; embedded tables retain explicit local height bounds.
- Ordinary data lists default to creation time descending before pagination, with a unique stable tie-breaker. Explicit user sorting wins. Models with ordinal/sequence fields preserve their declared sequence. Do not sort or reverse a single server page in the browser; SQL result snapshots retain query order. Locally created rows without timestamps must be inserted at the front by their owning controller.
- Record action columns use the shared `TableActions` row appearance: icon plus text, no ordinary filled/outlined button chrome. Toolbar and dialog actions keep their own hierarchy; action permissions remain server-derived.
- Form component property extensions register typed tabs with stable keys, labels, mandatory icons and independent content components. The generic designer owns tab layout; component-specific fields and index configuration belong to their own tabs.
- Detail rows edit through the owning form's field registry and validation paths. Preserve aggregate versioning, field write policies, bounded scrolling and server validation. Never create a second uncommitted form buffer inside an inline detail row.
- Business field validation must survive drafts, immutable publication snapshots, runtime projections and server aggregate writes. Text lengths count Unicode code points. User-configured patterns use bounded RE2 semantics in both browser and server; do not execute them through native backtracking regex engines.

## Mandatory Generated Business Resource Standards

- Authored application, page, directory and form labels reuse `LocalizedText` and the shared editor. Preserve optional metadata absence in legacy snapshots, propagate authorized translations through immutable publication and permission descriptors, and keep field/resource identities independent of display language.
- Application navigation changes use the application-owned durable intent and identity-owned managed navigation contract. Validate complete bounded trees, retain stable page identities and lifecycle/grant state, and fence stale publication/retry/cancel commands by navigation revision. Never update another module's resource tables directly.

- Generated business menus must share the same route identity function for rendering, selection and expansion, including directories without a URL. Verify navigation, tab switching and restoring a saved URL.
- Dynamic records must inherit the platform tenant, creator department, creator/updater and audit timestamp semantics. Populate these fields on the server; keep them separate from editable business values and reject attempts to write them through business payloads.
- Publish the generated page's data/field permission descriptor with its resource generation, including owned detail models. Permission discovery must respect the active tenant and actual page grants. Refreshing metadata must not enable offline resources or restore grants.
- Bind business field grants and data-scope expressions to stable field identities, not mutable storage column names. Enforce policy on the server for lists, counts, detail reads, filters, sorting, writes and historical snapshots. Hidden and masked fields must not be usable for query inference; UI visibility alone is not enforcement.

## Mandatory Platform Event Standards
New cross-service business events must use `simplepoint-events-api`, the transactional JDBC outbox/inbox and the RabbitMQ adapter. Business modules must not publish directly with RabbitTemplate, use local Spring events/Redis PubSub as durable cross-service delivery, or couple themselves to another module's persistence tables.

- Publish inside the same writable database transaction as the business fact. Handlers commit local effects, inbox completion and outgoing completion events atomically; remote effects belong to a separate event/operation.
- Use explicit versioned JSON contracts, stable event/subscription IDs, tenant/resource scope, operation IDs and generations. Never serialize Java type names, credentials or user authorization snapshots. Validate trusted producer and schema; fence stale generations.
- Authorization bootstrap queries must explicitly exclude revoked grants; do not depend on request-scoped soft-delete filters. Re-online must not restore revoked ordinary grants, including grants cached before the revocation.
- Keep durable event transport health observable separately from business readiness. Broker downtime must not remove otherwise ready outbox-backed services from RPC discovery; database unavailability must still prevent readiness.
- Delivery is at least once. Broker confirmation is not business completion. Required lifecycle participants must report durable completion before the owning operation is considered complete.
- Provision durable subscriptions before enabling producers; use separate service identities and broker ACLs, mandatory routing, correlated confirms, manual receipt ACK, bounded retries, audited dead-event replay and backlog monitoring. See `simplepoint-events/README.md`.
- Formal resource offline must revoke grants in the authorization-owning module, invalidate authorization versions and preserve data/history. Re-online must not revive previous ordinary grants. Client-side visibility is never the authorization boundary.

## Testing Guidelines
Run backend tests with `./gradlew test`. Place Java tests in the matching module test tree, mirroring production package names, and name test classes with a `*Test` suffix.

For frontend changes, run `pnpm typecheck` at minimum. If adding test tooling or tests, keep them near the feature they cover and use clear names such as `UserTable.test.tsx` or `permission-utils.test.ts`.

## Commit & Pull Request Guidelines
Recent history uses Conventional Commit-style prefixes such as `feat:`, `fix(i18n):`, and `chore:`. Keep commits focused and use a short imperative summary, optionally scoped: `feat(permission): add field scope editor`.

Pull requests should describe the change, list backend/frontend impact, link related issues, and include screenshots or screen recordings for UI changes. Mention any required config, migration, or data-permission behavior changes, and include the commands used for validation.

## Security & Configuration Tips
Do not commit secrets, generated credentials, local IDE files, or environment-specific configuration. Keep mock service worker assets in the frontend `public/` directory and document any new required environment variables in the relevant README.

## Mandatory Form Extension Standards

- Add declarative component capabilities through the versioned backend registry and frontend component/property/behavior registries. Keep component-specific configuration, previews and runtime adapters outside the designer controller. Reuse SForm widgets and platform tables/actions.
- Form list defaults bind stable field IDs and remain independent of scene layout and personal column preferences. Provide pointer and keyboard drag ordering; never require users to enter ordering numbers.
- Field create/edit visibility and writability policies intersect role field grants and lifecycle policies. Enforce blocked writes on the server, including owned detail fields and older page versions. Operation visibility must not be presented as a replacement for read authorization.
- Preserve absent optional metadata in immutable legacy snapshots. Cover canonical serialization, publication, runtime projection, direct API bypass and cross-scene field reuse when extending contracts. Component option domains and defaults require bounded server validation; Markdown must not execute raw HTML or unsafe URLs.

## Mandatory Module Composition Standards

- Keep logical module, API contract, resource and event identities independent of deployment host names. Reuse the same domain implementation in microservice, aggregate and mixed deployments; do not copy business code into a standalone service.
- Discover module contributions from their authoritative declarations. Derive configuration where possible and reject missing dependencies, incompatible versions and duplicate providers/routes explicitly; never select a provider by classpath or discovery iteration order.
- Declare new composable domain modules with `@PlatformModule` and their classpath index. Separate mandatory local dependencies from remotely resolvable contracts; derive capability names from interface annotations. Use exclusive package ownership and selected-module scanning, without a parallel global business scan. Do not treat every Gradle project as independently deployable when it still accesses another project's repositories.
- Inject RPC clients from an owned module component/configuration and declare every consumed contract, including self-consumption. Modular clients bind identity at the injection point; do not resolve unowned clients with `ApplicationContext.getBean`, select a caller from request data, or reuse a host credential across modules. Keep module credentials outside source/default metadata and provision caller policies with the deployment plan.
- Declare shared startup work in the owning module's `initializers`; derive its RPC dependencies from `@ModuleInitialization`. Use only the framework-bound initialization context for its RPC clients and exact module assets. Prepare declarations before applying remote effects, fail startup on required registration failures, and support restarting after partial success. Do not scan all classpath declarations in a modular host or silently use a host identity for unowned bootstrap code.
- Bootstrap base-data tasks precede declaration registration and retain declared cross-module priorities. Bind durable bootstrap state to the logical module and its data, not the physical host. Do not treat missing completion acknowledgements as failed business effects, replay an uncertain RUNNING action, or bypass legacy-state migration by changing/deleting contribution keys. Recovery must fence old executors and verify business outcomes.
- Local and remote invocation must preserve authorization, final-user scope, declared error/precision semantics and domain transaction boundaries. Co-location must not bypass trusted-caller validation or silently enlarge transactions; separating a module must not split an atomic aggregate.
- RPC operations must explicitly declare idempotency before enabling transport retries or fallback. A timeout or HTTP 5xx does not prove a write failed; trace IDs are not durable idempotency keys. Never recover provider, authorization, protocol or local invocation failures through generic business fallback.
- Public remote contracts must use transportable DTOs and explicit operation identities. Keep entity CRUD, persistence resources and framework helper APIs inside their domain; inheriting an internal base service does not make all its methods valid RPC operations.
- Bind repositories, migrations, jobs and durable events to their owning module and storage. Outbox writes remain in the business transaction. Multiple logical event identities in one host must retain producer authentication and broker isolation.
- Cross-module display projections use bounded, versioned source contracts and consumer-owned minimal data. Keep staging separate from the active generation; fence stale workers and atomically commit each page with its cursor before switching a complete generation. Perform remote rebuild reads outside business database transactions; suspending a transaction still retains its connection and locks. Preserve server-side filtering, sorting, counts and paging when replacing cross-domain joins. Projection freshness never substitutes for authorization, and an old complete generation must not silently appear current after source failure.
- Modular JPA hosts use `@EnableModulePersistence` with the selected `ModulePlan`; do not combine it with broad Entity/Repository scans. Declare exceptional entity roots and mandatory co-storage through `@ModulePersistence`. Inject persistence resources from owned constructors/configuration factories; do not select business storage through `@PersistenceContext`/`@PersistenceUnit`, named `@Resource`, a host primary bean or global lookups. Keep module transactions and durable events on the same binding. Co-storage constraints propagate automatically; independent stores do not imply distributed atomic transactions. Versioned migration and legacy-state adoption must be verified separately from entity mapping startup.
- Shared HTTP/security adapters delegate persistence to the owning domain service; do not inject domain repositories/JPA/JDBC resources or start unowned database transactions in browser adapters. Authenticate and revalidate the account in identity, keep OIDC binding changes in OIDC, and never recover a uniqueness conflict by querying inside an already failed transaction. Revocation must fence stale binding references and preserve required history.
- Module schema migrations use `@ModuleMigrations` and the exact `db/manifest.properties` contribution. Keep owned tables, supported dialects and immutable versioned SQL explicit; derive installation order and history identity from logical modules. Reject incomplete coverage, unadopted existing owned tables, checksum drift and unsupported schema versions before applying changes. A zero baseline may only initialize an absent module schema without skipping any declared version; existing databases require a separately verified adoption. Do not auto-repair history, run clean, or treat ORM schema validation as a complete legacy adoption check. Native engine migrations and shared infrastructure tables remain explicit owned contributions.
- Shared schema adapters use `ModuleMigrationContributor` and declare capability requirements through `@ModuleSharedSchemas`. Derive one contribution per selected store; never repeat shared table ownership in business modules or silently accept a missing adapter. Contribution adapters depend on `simplepoint-data-migrations-api`; installers explicitly load the executor. Do not transitively introduce Flyway into business runtimes. Installation adapters must not load Spring, JPA, broker clients or domain implementations. Keep metadata discovery free of database access, secrets and runtime side effects.
- Third-party engines start only with their selected owning module and use its storage/transaction binding. Do not reintroduce classpath-triggered vendor Boot engines, select a global primary data source or run native DDL from a modular runtime. Keep privileged installation separate; original-host compatibility must reuse the same engine factory with explicit options. Verify transaction participation, mandatory engine policy and worker shutdown.
- Where a pinned vendor provides complete native DDL, contribute immutable, attributed vendor baselines through the existing migration SPI. Keep exact source provenance and compare against the vendor's native installation on a real database. Do not start an engine from metadata discovery, bypass legacy adoption or overwrite a published baseline when upgrading the vendor.
- Declare composable event owners through `@ModuleEvents` and reuse authoritative contract constants in manifests and handlers. Preserve historical producer/queue/ledger identities when moving hosts. Publishers bind to the requesting module; do not select identities from payloads, borrow host credentials, share module connection factories or enable runtime topology declaration in a modular production host.
- Keep domain HTTP adapters and frontend contributions reusable. Preserve logical public URLs when relocating modules; validate every packaged remote and asset in aggregate distributions.
- Module-specific security matchers must derive their mounting prefix through `ModuleHttpPaths` from the same selected module plan as MVC. A modular host must reject unowned adapters instead of silently exposing legacy paths. Bind node certificate identities to the mounted request path, and validate auxiliary listener ports against the actual host port rather than a legacy service default.
- Root-mounted protocol adapters must declare bounded `ModuleHttpRoutes` derived from their MVC mappings and native servlet path constants; never reserve the whole host. Dedicated protocol security chains and exception advice must remain within their owned paths/controllers, and their JWT decoders must not replace the host decoder.
- Shared HTTP prefixes must derive disjoint subtrees from the selected controllers' authoritative mapping declarations through `ModuleHttpRoutes`; do not maintain a second manual path list or force unrelated domains into one host. Reserve conditional controller paths independent of environment, reject duplicate classes/overlapping owners, and validate actual MVC mappings including wildcard captures. Gateway routes must use `ModuleHttpPlan.routes()`, not the mounting-prefix map.
- Declare optional browser adapters as selected modules with `@ModuleHttp` and explicit local domain dependencies. Keep domain implementations independent of HTTP adapters and adapters independent of runnable hosts. Prefix every MVC mapping consistently, preserve method/scope security, reject namespace conflicts and keep infrastructure endpoints separate. Historical resource ownership must not change just because an HTTP adapter receives a new module ID. Declare the complete resource owner with `@ModuleResourceOwner` and exactly one initializer marked `registersResources`; keep its RPC credential bound to the actual module. Do not split one owner snapshot across modules or hosts. Claim resource codes during startup preparation, and build modular request-scope catalogs only from selected explicit declarations.
- Before claiming a topology supported, run its real authentication, authorization, persistence, workflow, event recovery and frontend scenarios. A process starting, router unit tests, or a wrapper launching several old services does not prove a complete standalone deployment.
- Resource declaration registration must validate the complete snapshot before mutation, checking both code and path ownership. Never infer an ownership transfer from a collision or silently adopt unowned records. Preserve retained and foreign resources during retirement, including stale closure relations and indirect hierarchy changes. Snapshot validation does not replace trusted-caller authorization, durable concurrency control or explicit legacy adoption.
- Keep privileged routed registration separate from local domain management. Validate the authenticated service client against an exact owner policy before domain writes; derive that policy and runtime client identities from the same deployment declarations. Contracts that require local isolation must enforce it even in legacy hosts. Missing security contributions must fail closed, and local plugin installation must not expose an unguarded management interface as RPC.
- Resource catalog mutations must enter the identity-owned `ResourceCatalogWriteBoundary` before catalog reads, including plugin contributions and inherited CRUD variants. Keep its database lock and revision in the same transaction as resource/ancestor/grant effects. Missing installation or a preloaded catalog persistence context must fail closed; never clear uncommitted state or use a separate transaction to work around it. A catalog revision is not a deployment generation, and an old unguarded writer must not participate in a coordinated upgrade.
- Managed resource registration must check its durable deployment authority under the catalog write lock, using only the verified service client identity. Installation alone may advance or retire generations; use fresh deployment clients and exact compare-and-set/retry semantics. Retain retirement history, reject compatibility/plugin bypasses and never downgrade to an unfenced provider. Deployment retirement does not revoke business grants or replace formal resource-offline events. Client provisioning, secret delivery and stopping old binaries remain explicit installation work.
