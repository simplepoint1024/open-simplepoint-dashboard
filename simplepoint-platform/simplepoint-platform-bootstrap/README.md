# 平台初始化与模块组合

初始化登记保存执行状态；业务动作仍由数据拥有方的本地服务完成。登记数据库与业务数据库
之间不是一个事务，不提供“恰好一次”保证，也不因超时自动重放动作。

## 模块接入

在模块的 `@PlatformModule.initializers` 中选择 `PlatformBootstrapModuleInitializer`。
框架自动将 `PlatformContributionService` 加入模块消费集合，使用该模块绑定的 RPC 客户端。
identity、i18n、storage 已声明此贡献；原有用户、字典、基础语言数据和可选 MinIO 初始化复用原业务实现。
旧宿主成功登记的显式接管端口已接入 registry；完整领域 Boot、安装编排及安装侧认证仍待后续验收。

`PlatformBootstrapContribution` 继续由领域组件或 `@Bean` 方法提供。模块模式下，
框架根据实际工厂/组件类型与选中模块的包、ClassLoader 归属确定拥有方，
不以贡献的 `moduleCode` 字符串推断服务身份。历史 `rbac-core`、`rbac-tenant` 等标签、
贡献键、版本和校验和保留。未归属的贡献，或提供贡献却未声明初始化器的模块，会使启动失败。
可选贡献返回 `null` 表示未启用；贡献工厂不得直接执行业务修改。

所有选中初始化器先完成准备，再按阶段执行：

1. `BOOTSTRAP`：基础数据贡献按原有 `order` 跨模块排序。
2. `REGISTRATION`：资源、语言等声明注册。

同阶段、同优先级保持模块依赖及声明顺序。普通初始化器继续实现 `prepare`；
需要拆分排序的初始化器通过 `prepareTasks` 返回多个 `ModuleInitializationTask`。
初始化准备验证贡献元数据和重复身份；业务动作自身仍负责校验其运行输入，并支持部分失败后的恢复。

## 配置与登记身份

- 旧服务保留 `simplepoint.platform.bootstrap.services` 的宿主范围设置。
- 模块模式使用 `simplepoint.platform.bootstrap.modules`，为空时允许全部选中模块。
- `enabled` 与逐贡献开关仍有效；启用的模块初始化要求 `fail-fast=true`。
- 模块登记键使用 `module/{模块ID}`，不使用 `spring.application.name`。数据库中的
  `serviceName` 字段保留以兼容旧结构，但该保留命名空间表示逻辑模块。
- 同一模块迁往不同宿主时，须继续绑定同一份业务数据及初始化登记状态；本机制不搬迁数据。

## 状态与失败语义

| 状态/场景 | 模块模式行为 |
| --- | --- |
| 没有记录 | 可以申请执行 |
| APPLIED，版本与校验和相同 | 跳过 |
| APPLIED，版本或校验和变化 | 允许申请新修订；部署必须协调修订版本 |
| RUNNING | 要求恢复确认，禁止自动重放 |
| FAILED | 可以重新申请，动作必须能够处理此前部分成功的业务结果 |
| 业务成功，完成登记失败 | 保留不确定状态，不写成业务失败 |
| 业务失败，失败登记也失败 | 保留原始业务异常，将登记异常作为附加诊断 |

模块/旧宿主状态更新和接管共用 registry 数据库修订行锁；首次创建同样在该边界内完成。
并发争抢失败的一方不会执行业务动作。锁不跨越业务动作或远程调用，不替代跨库幂等与恢复。
完成/失败登记必须匹配 RUNNING 状态、版本与校验和。失败摘要只登记异常类型，不复制可能包含配置
或输入数据的异常消息。

H2 和隔离 PostgreSQL 事务测试覆盖首次创建、已有 FAILED 记录的并发争抢、接管回滚及并发重试；
尚未完成正式部署故障验收。
这里的版本检查不等于租约或执行代次隔离，不能在旧执行者仍存活时强行重置状态并启动新执行者。

## 旧环境迁移与恢复

如果新模块键没有记录，但同一历史贡献已有宿主键记录，登记器返回
`BOOTSTRAP_LEGACY_STATE_REQUIRES_MIGRATION`，阻止按“首次运行”处理已有环境。
不能通过删除旧记录或改贡献键绕过此检查。

registry 的本地 `BootstrapLegacyTransfers` 提供预览和接管，未暴露为 RPC/HTTP。
安装器必须先退出旧初始化执行者，再根据模块归属执行：

1. `preview(Identity)` 读取同一历史贡献的全部宿主记录（最多 64 个），返回版本、校验和、来源列表及完整记录指纹。
2. 仅所有来源均为 APPLIED、具有完成时间且版本/校验和一致时允许接管；RUNNING、FAILED、缺失、已有模块记录或冲突均拒绝，不自动选择一个“看起来更新”的结果。
3. 安装器保存操作 UUID、目标及预览结果，在新的写事务调用 `transfer(Command)`。持锁后重新核对完整来源，来源变化则拒绝；不能在已加载登记实体的事务内直接升级为写操作。
4. `module/{模块ID}` 目标在同一事务创建已完成的模块登记并记录接管凭据，保留全部旧记录与原始时间；换宿主不会重跑同版本贡献。
5. `owner/{拥有方}/{完成机制}` 目标仅持久退役通用执行，例如 `owner/identity/dictionary`。新拥有方须使用自己的接管流程核对业务数据并承接完成状态；registry 不访问其他领域表，也不假设两处提交是原子事务。

相同操作、目标与预期版本/指纹重试返回原持久回执；不同操作或内容不会覆盖已完成接管。
转移后通用 registry 拒绝旧宿主、未知宿主和错误模块的读取/状态修改；领域拥有方接管目标禁止通用初始化再次执行。
这里检查的是登记作用域，不能把请求中的作用域当作经过认证的模块身份。完整安装仍须撤销旧客户端、
配置模块调用方授权并验证实际 RPC 边界；本地接管端口本身不授予调用权限。
批量安装仍须逐项记录操作进度；当前端口保证一项贡献的原子接管，不宣称整个安装批次跨领域原子完成。

必须先执行 bootstrap-registry V2 迁移，再切换新二进制。迁移只添加目录锁与接管表，不修改历史登记。
旧二进制不执行新保护，退出旧执行者仍是安装编排的必要前置条件；不能通过重置记录强行接管仍运行的任务。
字典拥有方已提供独立的[旧数据接管端口](../simplepoint-platform-dictionary-registration/README.md)，
安装侧字典适配器已通过独立持久日志衔接两个拥有方的回执；自动归属映射、凭据/配置发布、实际进程退役及完整部署编排仍待完成。
RUNNING 的恢复同样需要确认旧执行者已停止，并核对业务实际结果；自动租约重试、带执行代次的恢复
协议及管理操作尚未交付。

OIDC/通知字典已使用独立注册契约及原子完成状态，旧 Common 适配器继续用于兼容入口；
旧字典数据接管与共享 locale 查询等剩余贡献仍需迁移。不要只把现有服务切到模块启动注解就部署到已有数据库。
