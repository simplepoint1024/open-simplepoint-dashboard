- 遵循根目录 `AGENTS.md` 全部规范。页面复用 SimpleTable/DataTable/TableActions/SForm；不重建 CRUD 控制器、权限体系、事务回执或消息框架。

- DNA 的可信定义使用稳定字段 ID、作用域 ID、模型 ID 与不可变 schema 引用。不得携带客户端 SQL、任意脚本、授权快照、Java 类型名或数据库凭据。当前物理列名通过可信 schema 解析。
- 公式属于发布定义，普通记录请求不可选择表达式/版本或写入计算结果。计算输出只在服务端内部路径可写，不能以一个客户端可伪造的布尔值绕过保护。
- 每次提交用一个固定时间上下文；精确金额使用十进制，不经 JS Number 中转；明确 ROUND，错误不可静默置零。依赖编译包含未执行分支与空明细。
- 普通字段与计算字段共享类型、必填/长度/RE2/选项约束、查询索引和显示能力；计算字段的值由服务端产生，设计配置不等同于允许人工覆写。
- 所有来源字段的传递读取权限限制派生字段；隐藏或脱敏来源不可通过筛选、排序、计数、详情、公式预览、错误信息或历史快照推断。字段身份不随重命名改变。
- 发布、回填、激活复用 DNA 写策略锁和操作状态。跨服务异步事实使用平台 outbox/inbox/RabbitMQ，明确完成确认和 generation，不直接改其他模块表。
- 历史缺省元数据不改变序列化与 checksum。普通发布、取消及幂等指纹继续兼容；新增定义必须进入请求指纹，不能与无公式发布共用身份。
- 业务 SQL 仍走 Calcite；仅平台事务锁、回执及定义元数据允许已隔离的方言基础设施 SQL。
- 每阶段先有可审查的契约及失败测试，再实现；测试必须覆盖真实边界，不以 mock 返回计算值证明数据库已正确计算。

## 4. 计算定义、事务和激活设计

### 4.1 定义与持久化

DNA 使用版本化的聚合计算定义：父模型、主字段公式、按稳定明细 ID 绑定的子模型及公式；每个模型关联不可变 schema 版本/checksum。公式引用稳定 ID，编译器验证字段存在、类型适配、所有权、同数据源和循环依赖。

定义由授权的 APP 发布流程安装；DNA 重新核验实际模型及 schema，不能仅相信请求内声明。定义与激活版本应存放在受保护物理目标的事务元数据中，避免控制库读到新版本而业务库仍旧版本。查询授权所需传递依赖由可信编译得到，不能接受浏览器提交的依赖列表。

### 4.1.1 目标库升级与安装边界

- 不可变定义表为 `simpoint_dna_record_calculations_v1`，与业务表位于同一目标库/命名空间。按租户、模型、写策略版本读取最新的已安装记录；确定性主键禁止覆盖同版本定义，校验和与有界 JSON 校验在执行公式前完成。
- 该表只能在最终激活事务里写入。不能把未来版本的待发布定义提前写入此表：取消同样消耗写策略版本，提前写入会让取消后的版本误读到未激活公式。回填暂存需独立元数据。
- 新表由管理面的 `RecordWriteFenceProvisioner` 复用受检 DDL 计划创建和校验，普通数据写入不自动建表、不把缺表错误降级成“无公式”。
- **开放此批 Record 后端业务流量前必须完成基础设施升级。** 使用现有 Runtime 治理 `prepareStorage` 重放各现役命名空间的 ACTIVE schema 发布，核验新表以及旧业务 schema、记录计数、写策略版本均正确；再开放新后端业务流量。不可在缺表状态直接滚动接流量。管理重放及升级脚本/恢复演练纳入 P3/P8，不以实库测试已建表代替线上升级。
- 首次升级时，旧运行包还没有计算表 provisioner。可先用待部署发行包的 `RecordCalculationSchema` 与可信目标方言只读生成基础设施 DDL，核对真实绑定命名空间后，在备份完成的目标库事务内执行。此路径只允许新增计算元数据表/索引/注释，须以完整 schema checksum 回读核验；不修改业务行和写策略版本。部署后仍须通过已授权 `prepareStorage` 验证管理重放幂等性，不能用手写近似表结构或运行时自动补表代替。
- 当前主从执行预读的只是不可变定义及模型元数据；目标事务取得写策略锁后重新读取并核对定义。所有参与计算的业务输入在同一物理事务读取，内部完整字段读取保留租户/行权限，不作为 API 响应。单表创建、更新、删除及通用事务现已复用相同计算准备边界；直接使用预编译 SQL 的内部路径仍拒绝活动计算/校验定义，防止遗漏适配的调用方绕过计算。

### 4.2 写入顺序

1. 校验功能、租户、资源、记录与字段写权限；构造原始业务意图指纹。
2. 开启目标 READ_COMMITTED 事务，获得资源及写策略保护；精确重试先取原操作结果。
3. 对修改/删除获得主记录版本保护；加载完整持久化主从输入，合并合法变更、缺省值与明细增删，不读取其他租户或其他父记录。
4. 读取当前激活的可信计算定义，按稳定身份映射输入，在一个固定上下文内计算；即使用户看不到某来源值，也由受保护内部读取完成计算，输出仍按当前权限裁剪。
5. 类型/业务约束全部通过后，经 Calcite 写主表和明细；任何失败回滚所有记录、版本、回执与快照。
6. 原子保存回执与需要的提交快照，再提交。响应丢失后的相同请求返回原值，不重新执行 NOW/TODAY。

普通单表 Record API、通用事务 API、聚合 API 都必须接入；受管子表仍禁止独立写入。历史页面请求不能选择旧公式。删除明细后汇总更新，清空明细时遵循函数和必填语义。

### 4.2.1 通用事务与字段约束

- 通用事务按原始顺序逐步准备并执行，每步读取同一物理事务中前面的写入；主从重算也在该事务完成。一个事务共享固定微秒时间，单条创建沿用持久化创建回执的时间。
- 每个逻辑操作只返回主记录回执。所有操作完成后，将完整回执与数据/快照一起提交；唯一操作身份使并发重复批次的失败方整体回滚，再读取成功方回执。客户端载荷、字段授权、版本和资源校验仍在服务端。
- 一个请求仍至多 100 个逻辑操作，整个物理事务至多 401 条业务变更（含服务端派生的明细变更），超限整体回滚；这不是此前延期的跨数据源/分片批量写入。客户端每个 mutation 的 100 字段上限不限制服务端根据可信 schema 生成的计算列，内部生成值仍逐字段执行类型/必填/权限边界校验。
- 可缺省 `RecordFieldConstraints` 按稳定字段 ID 绑定在主/明细定义；未提供规则保持原有 JSON 与 checksum。包含 Unicode 码点长度、有界 RE2 pattern、最多 200 个精确类型标量选项；普通输入和计算输出均校验，输出在被后续公式引用前完成校验。主从同名 ID 不共享规则。
- 必填/精度/物理容量沿用不可变 schema，提交时必填仍属于表单提交生命周期。可选空文本沿用平台语义，长度/正则不把空值改为必填；标量选项继续按显式选项集合判断。DNA 不存储 UI 正则提示文本，也不把提交值放入错误参数。
- APP 发布到 DNA 的规则投影、组件特有选项约束与提交生命周期联调仍属于后续集成门禁；底层规则测试通过不等于真实业务表单已发布可用。

### 4.2.2 读取与历史授权的必需边界

- 当前 `writePolicyVersion` 是准入条件，刻意不进入业务操作幂等指纹；不能用调用者再次提交的该值推断已提交快照采用了哪个公式版本。
- 计算快照须在目标事务内绑定可信的已激活计算版本/校验和；历史读取按该绑定解析当时完整依赖，并叠加当前字段授权。移除公式、重命名字段或换新版页面都不能让旧计算值绕过其历史敏感来源权限。
- 列表、数量、筛选/排序、详情和历史读取均需传递依赖裁剪。回填分批期间还必须在目标读写边界阻止访问中间状态；仅在控制库设置状态、仅锁写入或仅隐藏 UI 均不足以证明无混合读取。
- DNA 的普通读取已在资源共享锁及目标策略共享锁内执行，主从读取和分页/计数共用目标连接；读取隔离级别为 READ_COMMITTED，保证已准入策略不变，不宣称分页数据具有可重复读快照。主从读取另核对前后主记录版本。
- 未安装计算定义的普通快照继续写入旧格式，支持当前基础版本回退。安装过计算定义（包括显式清除）的快照使用内部 v2 信封，保存真实安装版本与规范化定义校验和；历史定义丢失或不匹配时拒绝读取。正式开放公式后，回退目标必须支持此信封和相同授权语义，禁止仅降级二进制绕过该条件。

### 4.3 变更与回填

实现受管发布操作状态：准备、回填、待激活、已激活、失败/取消。状态名称按现有发布领域统一，禁止再造无关联的第二套发布控制器。

- 预检查：计算新定义、影响记录数、缺失输入、类型变化、索引/约束变化和历史页面影响。
- 有界数据可在独占发布锁下回填并激活；较大数据采用持久化批次、稳定游标与断点恢复。每批幂等，记录定义 checksum、版本及处理数量。
- 回填期间禁止普通读写看到部分新结果。优先复用受管资源维护/发布状态；如需要在线回填，必须先实现影子结果和原子切换，不能边改现有值边继续宣称在线一致。
- 失败保留可恢复状态，显示明确原因和重试入口；取消需恢复原定义和原值或丢弃隔离的新结果，不能把半回填状态标为可用。
- 激活前检查所有批次、校验和及并发栅栏；推进写策略版本，与数据完成同一目标事务。APP 只有收到持久化确认才完成上线。
- 旧审批快照不参与回填。发布重试、服务重启、消息重复和旧 generation 必须可验证。

### 4.3.1 分批发布协议与实现顺序

复用已有写策略发布/取消命令、APP 持久化意图和恢复入口。目标库的待发布日志与已激活计算定义表分开，不能通过提前安装未来公式来表示进度。

1. **进度与确认分开。** 发布结果可携带非终态 `STAGING`（暂存）、`APPLYING`（应用）或取消结果携带 `RESTORING`（恢复）。进度包括协议版本、目标库持久化单调序号、当前阶段已完成/总主记录数和可选稳定诊断代码，不包含记录值。计数达到 100% 仍不代表提交；只有既有目标版本/指纹的终态确认才能推进 APP 准入和页面激活。
2. **持久化原决定。** APP 保存原命令及最新目标进度；低序号响应忽略，同序号不同内容拒绝。取消恢复仍保持 `CANCELLING` 与旧准入版本，不得将 `cancelled=false` 的恢复进度解释为“原发布已经提交”。新响应只有在包含进度时才扩展 JSON；旧发布/取消响应保持原序列化形状。恢复始终使用原意图，不重新编译后来修改的草稿。
3. **目标维护边界。** 在原目标写策略互斥边界内取得维护所有权，固定规范化候选定义、目标版本、原策略、时钟和操作者。普通主/明细读写、计数、快照和重放读取都必须检查同一维护状态；结构与资源管理变更也须与该操作互斥。仅在 APP 标记发布中不能替代目标检查。
4. **稳定游标与撤销日志。** 按主记录稳定身份分批读取完整聚合，使用同一候选定义和固定时钟计算；保存候选结果及恢复所需原值/版本/审计元数据。每个聚合的暂存、每批应用及其游标/序号更新在各自目标事务原子提交，实际业务写入复用 Calcite。批次之间保持维护保护，不向普通请求暴露部分新结果。
5. **最后激活与取消恢复。** 完成所有应用、定义/结构/资源校验后，在同一目标事务安装不可变计算定义并推进写策略，才解除维护。取消先持久化恢复决定，分批恢复已应用的聚合，最后消费原目标版本但保留原计算定义；恢复未完成或结果未知时继续保护。已经确认激活的操作继续完成原 APP 发布，不伪造取消。
6. **故障与升级验收。** 覆盖每个提交点之前/之后的失败、响应丢失、重启、旧进度回放、取消与激活竞争、较大数据及旧页面；逐行比较恢复结果，验证读写/管理旁路都不能看到中间状态。新 APP 消费协议及目标存储升级先就绪，最后才解除公式发布保护。此前现有公有入口继续拒绝公式发布。

当前已实现进度契约、APP 持久化/编排、目标库发布意图与检查点日志、聚合候选值/撤销值的分块存储和可信业务补丁编译器，以及 Record 普通读取、写入、重放、快照和旧发布/取消入口的维护准入；结构与资源管理互斥及控制事务封装已实现。目标事务内的分批状态机已组合读取、计算、暂存、应用、撤销和最终激活；控制模型锁、可信元数据解析和目标状态机的内部协调入口已接通；公有发布/取消服务的授权、准入、进度/错误响应和审计已接通；可信 APP 定义已从不可变版本投影并随原发布意图持久化；连续调度已部署，最终 UI 进度与业务写入/提交集成仍待完成。底层实库场景不能代替最终业务发布验收。

聚合暂存契约：

- `simpoint_dna_publication_stages_v1` 保存每个主记录的清单、原意图摘要、负载摘要和 STAGED/APPLIED/RESTORED 状态；`simpoint_dna_publication_chunks_v1` 保存不可变数据块。清单与全部块在同一目标事务内提交，随后一起推进发布检查点；不能在自动提交连接上逐块写入。
- 负载只包含稳定字段 ID 对应的计算字段原值/候选值、原记录版本及更新人/更新时间，不复制整个审批快照、授权信息或无关业务输入。精确值复用 `LogicalValue` 表示，字段类型/当前列名仍须由后续执行编译器按冻结 schema 验证和解析。主记录及其最多五组、每组最多四十条明细校验归属与重复身份。
- ASCII 转义的规范 JSON 按 64 KiB 分块，逐块及整体 SHA-256 校验，分块读取每页最多 32 块；重复键、尾随内容、非规范整数、缺块、错序、错误身份及摘要不一致均拒绝。一个聚合的编码负载上限为 64 MiB，写入 SQL 生成前即有界序列化；这是可恢复发布操作的资源预算，不改变普通业务文本写入限制，也不使用审批快照的 2 MiB 上限。总记录数通过稳定游标分批处理。
- 清单更新比较原意图摘要、租户/模型/目标版本/发布指纹、原状态/序号以及完整负载身份。应用和恢复标记必须与实际业务修改、发布检查点在同一物理事务提交。取消只恢复已应用聚合；未应用的隔离候选值不会进入业务表。清理仅能在终态后的保留策略下开展，当前未提供清理入口。
- 已实现可信 schema 下的参数化补丁编译：冻结的活动/请求 schema、物理位置、资源代际、APP/表单和主从归属须一致；按稳定字段 ID 解析当前列名，复用普通写入的精确类型转换，拒绝非规范值、默认值冲突及明细归属/顺序列。应用与撤销都比较租户、记录版本、更新人/时间及明细父记录；撤销恢复原版本与更新审计，创建信息和其他字段不变。调用方必须持有维护锁，检查每条影响行数严格为一，并将业务 SQL、聚合状态和检查点原子提交。公有发布/取消服务已接通；后续仍须完成可信 APP 投影和连续编排，再进行 B1–B5 的真实回填/失败恢复验证。


### 4.3.2 Record 维护准入与管理互斥

- Record 读取在目标策略共享锁后检查持久化发布日志，使用同一连接、同一 READ_COMMITTED 事务完成查询。普通主从读取、计数、历史快照、提交回执和计算定义预加载均受保护；内部完整性检查、创建结果确认和写失败诊断也改用带租户准入的查询。明细管理检查使用主模型的维护所有权。
- 写入回执在维护检查之后读取，但仍保留“已完成操作可跨写策略版本返回原回执”的幂等语义；新的写入才比较请求版本。提交结果未知时的回执恢复重新取得共享锁并检查维护状态，不能从新连接绕过保护。
- 旧同步发布/取消入口先取得排他策略锁并检查维护状态；非终态回填未结束时，不运行预检查、不推进版本，也不直接取消已应用的数据。正式分批执行器将使用独立的受信恢复入口，不能借用旧取消快捷路径。
- 暂存/应用/恢复期间持续拒绝普通访问，阶段计数达到 100% 不放行。查询同时核对“目标版本尚未消费”的日志，防止仅把日志改成终态就提前开放；基础设施缺失或日志不一致时失败关闭。DNA 返回稳定冲突代码 `RECORD_MAINTENANCE_IN_PROGRESS`，APP 使用既有“发布正在处理中”的错误提示。
- `RecordMaintenanceControl` 已接入模型版本创建、新明细注册、结构发布 claim/retry、资源 bind/unbind/project 和离线事件。先从不可变归属关系扩展受影响模型及主模型的集合，再按统一顺序取得控制库模型写锁；等待结束后通过带写锁的 `refresh` 使用最新实体，避免 JPA 缓存中的旧版本在刷新前触发锁查询冲突。没有所属主模型锁、缺少控制事务或租户不符时拒绝检查。
- 资源变更保持“资源投影 → 排序后的模型/主模型 → 目标策略”锁序。切换资源保护旧关联和新关联，离线保护所有将撤销的关联。普通模型管理在控制模型锁内检查目标日志；检查结束可释放目标读事务，但控制锁一直保持到元数据修改提交。回填事务也必须先取得同一模型集合的控制锁，所以检查与管理提交之间不能插入新的回填认领。
- `RecordPublicationControlFence` 为受信分批执行器提供有界控制事务：锁内刷新全部模型、确认 ACTIVE，再运行包含提交的目标事务。执行器此时不能反向获取资源锁；资源关联快照读取由资源变更必需的模型锁保护。目标日志是唯一持久化维护事实，没有第二份跨库维护标志；目标认领已经提交而控制事务随后失败时，后续管理仍读取到维护日志并拒绝修改。
- 离线事件遇到维护会抛出稳定冲突并回滚本地效果，不发送完成事件；目标取消/完成后可以重试。事件继续沿用平台的有限重试和审计死信重放，正式 B5 尚须验证延迟消息、较长维护及跨服务完成确认，不能把本批事件处理器测试等同于真实消息链路终验。现役环境仍保持发布保护；源码中的 DNA 公有服务已连接内部协调入口，APP 表单发布拦截仍保留，下一步接入可信定义投影与连续编排。


### 4.3.3 目标事务分批执行与下一步接入边界

- `RecordPublicationBatchExecutor` 在一次借用的目标事务内执行一个有界步骤，单批最多十个主从聚合。目标会话持有根模型排他写策略锁，只有后端负责提交和回滚；调用方必须先持有控制侧模型锁。公有 `RecordWritePolicyService` 的显式计算定义分支现已通过协调器调用此入口；未提供计算定义的旧命令保留原同步路径。
- STAGING 按主记录 ID 的数据库排序推进游标，每次读取一个完整主从聚合；宽模型按列分组查询，同一事务核对各组记录身份和版本。使用冻结时钟计算，仅保存变化的稳定字段原值/候选值；明细有变化时主记录参与版本更新，无变化聚合仍有清单但不改业务数据。
- APPLYING / RESTORING 从校验后的持久化块重建补丁，按原版本和审计元数据执行业务 SQL。业务修改、清单推进和检查点序号在同一物理事务提交。批次请求带预期序号，过期重放只返回已提交检查点，未来序号拒绝；失败诊断也比较原序号，不能覆盖已提交结果。
- 最终激活核对各状态清单计数、主记录总数、可信历史 schema 下的完整性与值约束，再原子安装目标计算定义、推进写策略并终结日志。预检查失败仍保持维护，可记录稳定诊断并进入恢复。取消只撤销已应用聚合，最后消费目标版本、保留原计算定义。
- **受信资源快照已补齐：** 版本二意图按模型保存完整资源代码 → 绑定身份/投影身份/归属/代际集合，包括空集合及历史无投影关联；版本一仍保留原规范 JSON 和校验和。版本二不使用旧标量代际，各资源独立核对，禁止最大值或模型版本替代。解析器只接受持有当前租户模型写锁的控制事务，以有界标量查询读取活动绑定并显式排除已撤销关联，拒绝绑定到离线或其他模型投影的矛盾元数据。
- `RecordPublicationCoordinator` 首次仅提交维护认领，随后每次在新的 READ_COMMITTED 控制事务中锁定模型、读取受信快照并执行一个目标批次。恢复沿用原命令、操作者、时钟和计算定义身份，不重新冻结草稿或将当前资源代际覆盖原快照；单次目标工作预算不超过三十秒且在元数据读取后扣除已用时间。已终结请求经原策略/定义身份验证可回读，不因后续正常资源代际变化而重做业务修改。
- 非终态失败的诊断通过新的受保护尝试持久化，比较失败前序号；原错误保持权威，诊断失败不能改变业务结果。版本一非终态日志没有可信资源身份，不自动猜测或升级，需显式恢复处理；该兼容约束来自开放前设计；当前正式公式发布已经开放，受信版本二意图的恢复见最终验收。
- 资源绑定/解绑的维护检查必须位于“已有绑定/无绑定”提前返回之前：建立资源锁记录本身也可能新增历史资源投影。否则所谓幂等请求会改变被冻结的资源关联，后续恢复校验将失败。
- 下一步顺序：可信 APP 计算/校验定义投影 → APP 原意图恢复与连续调度 → UI 进度/错误操作 → 目标存储升级与部署 → B1–B5 真实表单、流程、MQ、重启/恢复验收。

### 4.3.4 公有服务与分批校验响应

- 公有管理服务先校验管理权限、租户及模型归属，再取得平台执行准入，显式计算定义走受保护协调器；旧缺省计算定义的同步发布/取消保持原语义。授权和审计不迁入通用计算库或 UI。
- STAGING/APPLYING 进度返回原准入版本；RESTORING 返回原版本且没有目标指纹。只有已提交或已取消的终态返回目标版本及对应指纹。已经取消的操作不能由迟到发布请求重新开启；取消遇到已提交发布则返回原发布确认。
- 最终校验不通过时，先回滚当前目标尝试，再按预期序号持久化诊断。仅在确认得到同一次失败的持久化 APPLYING 检查点时，响应才同时返回其序号与聚合违规计数；必须已处理全部记录，且失败代码为 `RECORD_WRITE_POLICY_PRECHECK_FAILED`。诊断未确认或恢复方向已变化时抛出稳定错误，不拼接过期检查结果。
- APP 保存带序号的最终检查结果，拒绝同序号不同计数，旧进度不能覆盖新失败。存在违规计数时 `targetInProgress` 为 false，走现有“数据冲突/检查报告”处理，不继续假装执行、不激活页面；维护仍保留，用户可按原意图重试或取消。原始缺省进度的旧响应保持字节兼容。
- 进度只记录有限标签的执行指标，不产生“发布成功/发布失败/已取消”审计事件；终态成功及实际校验/执行失败沿用平台审计。正常短批次不按告警刷日志，超时慢批次仍受性能日志监测。
- 发布部署顺序仍需保证消费该响应语义的 APP 与目标存储先就绪，再放开公式表单入口。2026-10-18 已将本批 DNA/APP 部署为 `20261018-publication-service1` 并完成现有业务回归；APP 公式表单发布入口仍受保护，不能把底层部署当作终端计算业务已交付。

### 4.4.1 计算后聚合校验契约（2026-10-19 已部署，完整业务集成待终验）

- `RecordCalculationDefinition.validations` 是可缺省的不可变发布元数据；旧定义不补空属性、不改变原 JSON。`RecordValidationField` 引用稳定作用域/字段 ID，条件复用平台的两值运算语义；无 SQL、脚本、APP 类型、UI 消息或权限快照。
- 支持条件必填、精确数值范围、同类型时间先后、明细数量、主从精确合计；明细字段范围及必填逐行执行，条件只能读取本行和主表，禁止跨明细集合的模糊单值引用。定义编译检查所有分支，不能在恒假条件中隐藏未知字段或错误类型。
- 条件字面量保持原精度，不按物理列的小数位、长度或微秒截断；NULL 比较先为假，再应用 NOT/NOT_EQUALS/NOT_IN。JSON 缺失使用既有规范语义，文本缺失包括平台约定的 Unicode 空白。定义树深度、展开节点、规则数及字面量总量均有上限。
- `RecordCalculationEvaluator` 先用本次输入计算，再合并新输出进行聚合校验；请求携带或数据库留下的旧计算列不进入这个结果集。失败发生在准备写入时，沿用原目标事务回滚、版本、回执及快照机制；独立 `simplepoint-calculation` 不引入平台依赖。
- `FormCalculationValidationProjection` 从不可变治理文档编译场景/祖先可见性、顺序覆盖的条件要求和聚合约束；计算字段的提交必填不会仅因其不可人工写入而变成草稿必填。规则身份可复现，UI 提示留在 APP。需要生命周期校验时，同时限定内部状态字段的合法取值，避免未知状态绕过条件；约束字段预算为 512，保留 300 个业务字段加内部控制字段的容量。
- APP 普通输入前置检查保留，历史约束、状态迁移、可信试算/流程预检和正式发布均已接入并验收。此处描述的是实际事务契约；最终交付以 §1.1 的真实业务、恢复及浏览器证据为准。

### 4.4.2 流程最终值与快照提交边界（实施要求）

- 预览与正式提交分别拥有固定计算时间，因此包含 NOW/TODAY 等表达式的结果可能不同。流程使用提交快照重新映射变量；不能复用预览结果作为最终业务事实。
- 对绑定流程变量的字段，类型兼容由可信发布绑定检查；最终快照还需在 DNA 物理事务提交前检查必填、字符串传输长度及用户/角色等格式要求。失败回滚主从变更、版本、回执和快照，避免留下无法启动流程的已提交数据。外部服务可用性等跨服务因素仍由原幂等恢复处理，不宣称跨库原子提交。
- 新增快照要求只允许收紧本次捕获，不得覆盖已安装规则。规则冻结到接受提交时的原意图，并进入 DNA 幂等指纹；不在重试时从后来编辑的流程重新生成。旧已接受意图缺省该属性时保留原序列化与指纹，不能使升级前已提交的回执失效。
- 快照字段仍按当前允许的读取范围投影；绑定要求不得成为隐藏/脱敏字段的读取旁路。DNA 不依赖工作流实现或 APP 枚举，采用有界、中性的字段值约束。
