# 工作流名称投影与身份目录解耦

日期：2026-10-21。状态：身份端版本化分页目录、工作流分代重建、列表读取版本复核、持久通知与后台接续已实现；受控恢复及正式部署尚未完成。

## 1. 目标与核对依据

对应模块组合计划 G22。改造前 `WorkflowReadSql.INBOX/MATTERS` 把身份的账户、租户、成员关系表关联到工作流记录；`WorkflowInboxQueries` 和 `WorkflowMatterQueries` 允许按姓名筛选、排序，`ProjectionPages` 在数据库中计算总数和分页。因此，仅对当前页调用名称 RPC 无法保持现有功能。

详情中的按 ID 名称解析继续复用 `AuditIdentityDirectory` v2。列表采用工作流拥有的最小显示名称投影，服务端 SQL 只关联工作流存储。该投影不参与授权、候选人资格或租户成员有效性判断；这些判断继续由当前安全上下文和身份契约负责。

## 2. 已实现：身份端一致分页来源

新增 `saas.member-label-directory:1`，只允许已验证的 OAuth `client_credentials` 服务身份和调用 scope。它是内部重建契约，不能直接作为浏览器选人接口开放。正式安装须按实际消费模块配置调用权限，不把拥有目录访问权解释为终端用户可以查看所有成员。

| 操作/类型 | 语义 |
| --- | --- |
| `revision()` | 返回持久化的安装 epoch 与非负 long 序号；不返回账户实体或权限快照 |
| `page(request)` | 一个租户、1–200 条记录、按身份存储的用户主键稳定续页，多取一条判断是否还有数据 |
| `expectedRevision` | 首次可省略；带续页 ID 时必须提供。版本不一致返回 `restartRequired` 和空记录，禁止拼接旧页 |
| `Label` | 仅用户 ID 与当前显示名；没有姓名/结构化姓名/邮箱时名称为 null，不回退 ID/昵称 |
| `tenantActive=false` | 该版本下租户不存在或已删除；不能把旧租户投影继续视为有效 |

页内版本、租户状态和名称查询在身份拥有的 `REQUIRES_NEW`、只读 `REPEATABLE_READ` 事务中完成，不受宿主主数据源或调用者事务影响。两个 RPC 之间不持有连接、游标或长事务。同一版本下续页可重复读取；源发生变化则整个未完成重建失效。

新增 identity **V2** 迁移，不改 V1。`simpoint_identity_member_label_revision` 保存单例 epoch 和序号，三组语句级触发器在业务修改前更新该行：

- 账户：创建、删除、清空，以及 ID、完整名、结构化姓名、邮箱、启用/删除状态的 UPDATE。
- 租户：创建、删除、清空，以及 ID、负责人、删除状态的 UPDATE。
- 成员关系：创建、删除、清空，以及租户、用户、启用/删除状态的 UPDATE。

触发器和原修改同事务提交/回滚；使用触发源 schema 明确定位版本表，不借用 `public` 或调用者搜索路径。版本表缺失时拒绝目录修改，不能静默丢失变更。完整 SQL/批量更新同样覆盖，不要求各业务服务手动调用刷新方法。只更新密码或授权版本等无关列的 SQL 不增加目录版本；ORM 若连同未变化的姓名列一起更新，可能保守增加版本，属于允许的额外失效。

这是显示目录独立版本，不能复用 `authorizationVersion`：当前姓名更新与权限版本的覆盖不同，也不能为刷新名称而扩大权限缓存失效范围。

当前采用全身份域版本，故相关写操作会竞争同一短事务锁，一个租户变化也可能导致其他租户的目录重建重试。优点是覆盖完整、无跨租户漏更新且消费者协议简单；它是明确的性能约束。持续高频目录写入场景须测量锁等待与重建成本，再在同一契约后演进分区版本/持久快照，不以无版本缓存换取速度。空 UPDATE 或更新为相同值也允许推进版本。

## 3. 已实现：工作流拥有的分代重建

`WorkflowMemberLabelStore` 负责所属存储上的短事务、持久租约及原子切代；`WorkflowMemberLabelProjection` 负责目录调用与分批推进；`WorkflowMemberLabelProperties` 由模块配置自动绑定有界默认值。workflow 已声明消费 `MemberLabelDirectory`，使用框架绑定的模块调用方，业务参数不能选择调用身份。

workflow V2 新增 `simpoint_workflow_member_label_state` 和 `simpoint_workflow_member_labels`，不改原 V1。活动代与重建代分开，源版本、已观察版本水位、续页位置、已完成页数/行数和租约持久保存。投影只保存 ID 和名称，不保存凭据、角色或权限。

- 每页最多 200 条；默认每轮最多 8 页、10 秒调度预算，每次重建最多 500 页（最多 100,000 名成员），每实例最多两个并发任务。默认租约 60 秒，本地事务超时 10 秒；配置有明确上限并校验时间关系。预算在步骤之间检查，已发出的调用仍遵循平台 RPC 的超时，不能把 10 秒宣称为强制中断任意网络调用。
- 每页写入与续页位置一起提交。预算耗尽或远端失败释放租约并保留已提交页面；进程消失后其他 worker 可以在租约到期后接续。完整但尚未激活的重建也可直接完成最终版本复核，不重新取页。
- 任一写入/激活均核对租户、代次、owner、数据库时钟租约和游标进度。旧 worker 的追加、激活、释放或清理不能影响后继 owner。每个 worker 都使用新的随机 owner，不复用宿主/线程标识。
- 完成后重新读取源版本，再在一个工作流事务中更换活动指针并清理旧行。重复 ID、混租户、错误版本/游标、超出预算等不发布部分数据。源变更时清理当前 staging，已观察版本水位独立保留；后续同 epoch 的旧版本不能因清理 staging 而被重新接收。旧活动代保留，但不能据此对外声称旧代仍是当前数据。
- 重建入口拒绝已有工作流事务，避免挂起事务仍保留原连接与锁；RPC 只发生在投影事务之外。列表已通过独立读取边界先准备投影，再开启读取事务，移除了包裹整个过程的 `@Transactional(readOnly=true)`。
- `READY` 仅代表已有完整代；`IN_PROGRESS`/`BUSY`/`RESTART_REQUIRED` 供后续任务调度使用。后台任务消费这些状态推进下一轮；对外查询仍严格检查当前版本。

以下为完整集成约束；重建和列表读路径已实现，受控恢复/epoch 轮换入口仍待完成：

1. 用工作流迁移定义租户投影状态和名称行，仅保存租户、投影 generation、用户 ID、名称、源 revision 及重建状态。禁止复制账户凭据、身份实体表或授权快照。
2. 按租户维护活动 generation 与独立的 staging generation。分批获取目录；每页校验租户、版本、页大小、游标进展和重复记录。源游标由源数据库排序定义，不能用 Java 字符串排序假设跨数据库 collation 一致。
3. 重建有总时限、页数/数据预算、工作并发和有限重试；超出预算报告不可用并可恢复后台执行，禁止加载无上限成员 ID 集合再拼 SQL `IN`。
4. 取完最后一页后再次核对源版本，只有完整且同版本的 staging 才能在工作流事务中替换活动指针。并发重建通过持久任务代次/租约排他，旧 worker 不得覆盖新指针；失败不覆盖已完成 generation。
5. 租户删除/成员停用/删除通过新版本的完整集合移除名称；空集合也是有效完整 generation。不能仅 upsert 收到的名字而永不清理离职成员。
6. 列表的 count、过滤、排序与记录读取固定同一个活动 generation 和本地读取快照。名称仍在数据库中筛选/排序，沿用原稳定排序补键。不得在浏览器或当前页重排。
7. 正式切换需要源版本校验。读取前确认投影版本，读取后复核源版本；变更则有限重试或返回明确的可重试错误。源不可用、未完成首轮重建或版本不一致时不把旧名称作为当前结果静默返回。允许展示的历史审计快照另走明确契约。
8. 新安装 epoch 不可与旧 epoch 比大小，必须重新建代；同一 epoch 序号倒退视为恢复/源损坏，需要受控恢复与 epoch 轮换，不能被旧消息自动降级。

版本复核提供可解释的读取时点，不宣称跨身份与工作流的分布式原子快照。权限验证始终独立、即时执行，MQ 消费进度不能成为授权依据。

### 3.1 已实现：列表的源版本复核与本地快照

`WorkflowMemberLabelReader` 是领域内部读边界；`WorkflowMemberLabelReads` 组织版本检查和有限重试，`WorkflowMemberLabelStore` 管理数据库快照与观察水位。业务查询继续通过 `ProjectionPages` 在数据库中执行原有筛选、排序、计数和分页。

- 入口先验证操作权限、租户和用户，再访问目录。列表使用 `WorkflowReadSql.MEMBERS` 的工作流活动代，SQL 不再读取身份的账户、租户或成员表。
- 源版本检查 → 有界重建（如必要）→ 一个工作流只读 `REPEATABLE_READ` 事务 → 源版本复核。所有源 RPC 均发生在本地事务之外；读取事务中的活动指针、观察水位、结果和总数共用一个快照。活动版本与已观察源版本都必须一致。
- 若查询后版本变化，丢弃整次结果并在短事务中保存观察水位，再有限重试；最多两次读取尝试。已经见到的新版本不会因请求失败、协调器重建或下一次源回退而被遗忘。同 epoch 版本倒退拒绝查询。
- 首轮重建未完成、其他 worker 占用租约、版本持续变化或者源不可用，都不返回旧名称作为当前列表。已完成的分页保留，后台任务或下一次请求可以继续。公开接口使用 `workflow.error.DIRECTORY_PREPARING` / `workflow.error.DIRECTORY_UNAVAILABLE`，保留内部诊断原因，返回 HTTP 503、`Retry-After`（2/5 秒）、`retryable` 与 `retryAfterSeconds`。中英语言包说明准备中或暂不可用；没有为业务写入增加自动重试。
- 概览复用相同列表边界，不在两个列表外再持有事务。每个列表内部保证总数与记录的一致快照，两个概览区块不宣称共享跨模块原子时点。
- 进度、重新提交详情和节点历史仍以授权后的有限用户 ID 调用 `AuditIdentityDirectory`；它们不需要完整租户投影预热。列表姓名不参与授权。工作流宿主继续禁用 Open EntityManager In View，重试不能复用带有旧实体的请求级持久上下文。

共享与独立存储绑定测试安装真实模块迁移、使用真实身份目录与 Flowable 原生记录，验证中文/补充字符改名、成员停用、姓名筛选/排序/计数/分页、任务和个人/租户边界，以及查询期间改名并完成任务后整页重试。独立存储用例使用两个数据源和不同 PostgreSQL schema，工作流 schema 不含身份表；尚未在两台数据库服务器上运行。源调用由测试服务主体在进程内验证；不等同于 HTTP OAuth 与正式宿主部署验收。

## 4. 已实现：持久版本通知与后台接续

### 4.1 身份拥有的观察事实

identity V3 保留 V1/V2，不修改已发布脚本。观察器在所属存储的短写事务中锁定源版本，公平选择至多 32 个待通知租户，将各租户观察游标和 outbox 同时提交。它发布的是“观察到已提交目录版本”，允许合并中间版本；不能将它解释为与原账户修改同时产生的逐条变更事件。未能取得版本锁时让出本轮。

事件为 `identity.member-labels.observed` v1，producer 保持 `common`，resource 为 `member-labels`；租户使用真实 ID，generation 为源序号，载荷只有 epoch。operation/correlation 由租户、epoch、序号确定；不传递姓名、身份实体、凭据或授权快照。消费端验证全部契约字段。平台信封的 tenant 上限与身份字段一致，为 255 个 Unicode 码点；其他标识限制及 32 KiB 信封限制不变。

V3 回填已有租户（包含软删除），触发器登记后来创建/改 ID 的租户，目录记录不随租户硬删除或 TRUNCATE 丢失。V3 之前已永久删除且不存在于库中的租户无法凭空恢复；工作流已关注的租户仍可通过周期复核发现源中不存在。观察顺序按上次观察时间与租户 ID 排列，避免持续更新时尾部租户饥饿。已经完整通知的版本空闲轮询不再扫描租户目录。

源单例分别持久化“最高已提交观察版本”和“该版本通知全部完成”。即使只完成一批，较新观察也不能被遗忘；同 epoch 序号倒退会拒绝观察。完成标记不能代替最高水位，也不能将部分通知解释为全部完成。outbox、租户游标或全局水位任一步失败均整笔回滚。

观察配置入口属于选中的 identity 模块，启用平台事件时自动启动。共用 tenant 实现依赖的 Authorization 宿主不会因此启动 `common` 的发布任务，也不会借用宿主主数据源。

### 4.2 工作流拥有的持久刷新任务

workflow V3 新增刷新队列，并为已有投影状态回填任务。首次查询在访问源之前登记关注状态，由同事务触发器登记队列；因此首次 RPC 失败后不需要用户再次打开页面才有机会恢复。

订阅 `member-labels.refresh` 的 handler 仅在 inbox 事务中登记已有投影的刷新请求。源目录调用在 inbox 完成之后由独立 worker 执行，不在消费事务或业务事务中保留数据库连接等待网络。尚未被工作流使用的租户不因收到通知而自动缓存全部成员。

刷新请求有持久 generation、租约 token、数据库时钟截止时间。重复/旧版本通知不会降级水位；不同 epoch 通知仅要求检查真实源。执行期间收到新请求时，旧任务完成不能吞掉新请求；旧租约也不能完成或释放后继任务。默认每轮 2 个任务、间隔 2 秒，完整状态每 60 秒对账；异常按 2 秒至 5 分钟退避，持久保留任务继续恢复。失败分类不记录提交值或异常消息。

`PeriodicWorker` 统一管理固定延迟任务、关闭与重启，不继承浏览器请求线程变量。单 worker 不重叠；关闭会中断并等待合作任务退出。非合作代码超过等待时间时保留执行器句柄，不能重启出第二个并行 worker；不宣称任意网络调用都能立即取消。

### 4.3 安装、运维与边界

使用平台 JDBC outbox/inbox 与 RabbitMQ adapter，模块声明自动派生事件归属。正式发布前需安装 workflow 的共享事件 schema，并预置 `sp.events.common` 与 quorum queue `sp.events.workflow.member-labels.refresh`，绑定 `identity.member-labels.observed.v1`。common/workflow 使用各自账号，运行期 configure 权限为空；工作流不能冒充 common，common 不能读取消费队列。

- 身份待观察指标：`simplepoint.identity.member.labels.pending`。
- 工作流刷新指标：`simplepoint.workflow.member.labels.refresh{state=DUE|LEASED|FAILED}`。
- 继续监控平台 outbox/inbox 积压、DEAD、隔离事件和 broker 队列；投递确认不是名称已刷新。
- Workflow 就绪探针与 Common/APP/DNA 一样使用 `readinessState,db`；MQ 故障独立告警，不使可保存 outbox 的服务退出 RPC 发现。
- 消息与周期对账改善时效，查询前后的源版本复核仍是防止把旧名称作为当前结果的边界。投影永远不替代授权。
- 全域版本的锁竞争与多租户重复重建成本仍存在；需要按实际负载测量，不能宣称无限扩展。

正式安装器、运行环境的账号/订阅预置、受控 epoch 恢复与完整 HTTP/浏览器部署验收仍待完成。
