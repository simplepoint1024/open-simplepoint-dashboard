# 平台账号与租户成员拆分

## 已实现的边界

| 身份 | 能力 | 不能做的事 |
| --- | --- | --- |
| 超级管理员（现有 User.superAdmin） | 原有应急最高权限；独立授予/撤销平台身份 | 撤销或停用最后一个有效超级管理员 |
| PLATFORM_ADMIN | 全局账号查看、创建、编辑与账号安全审计 | 授予平台身份、修改特权账号、自动访问租户业务数据 |
| ACCOUNT_ADMIN | 全局账号查看、创建、编辑 | 平台授权、安全审计、修改特权账号 |
| AUDITOR | 只读平台账号安全审计 | 账号变更、平台授权 |
| 租户所有者/管理员 | 当前组织租户添加已有账号、成员组织/启停、移除成员、租户角色配置 | 修改全局账号、密码或平台身份 |

这次先实现固定平台角色，不提供平台角色自定义 CRUD。PLATFORM_ADMIN 当前不是“所有平台管理页面”的通配角色；租户、应用、系统配置等已有控制台能力仍遵循原规则，未自动开放给它。

平台角色在独立的 identity/role 表中，不使用租户 Role 表；超级管理员仍兼容原 super_admin 标记。普通角色不获得 ROLE_Administrator 或数据隔离绕过权。

## 使用

1. 已有超级管理员登录，工作台切换至“平台”。
2. 打开“平台管理 → 平台账号”，找到已有全局账号，选择“授予/撤销平台身份”。
3. 选择固定角色，填写原因和当前操作者密码；已启用双因素时必须同时提供动态验证码。
4. 新授权账号重新加载工作台选项，选择“平台”后出现对应菜单。平台审计员使用独立审计页面，不依赖账号列表权限。
5. 组织租户中原“用户管理”变成“租户成员”。添加需要完整邮箱且账号已经注册；本次没有实现邮件邀请/接受流程。

创建全局账号也要求二次验证，初始密码为 12–64 字符；编辑入口只允许姓名和全局启停。个人资料、改密、双因素仍走现有个人设置入口，不提供管理员代设既有账号密码。只有外部身份且没有可用本地密码的操作者，需先通过现有可信账号设置流程完成密码配置。

## 安全与一致性

- 旧通用 User 创建/修改 HTTP 接口拒绝写入；UsersService 的通用修改和全局批量删除也拒绝。启动引导保留受信任的首次超级管理员创建路径，不会重置已有账号。
- 每次平台写入都重新检查数据库中的操作者身份；请求里伪造 root 标记或租户角色不生效。创建/编辑 DTO 禁止夹带 roles/superAdmin。
- 身份变更与账号停用使用数据库全局行锁串行化；携带账号 revision 防止覆盖并发编辑。最后一个有效超级管理员的有效条件是未删除、启用、未锁定、账号及凭据未过期。
- 写入必须提供操作原因。成功审计与变更同事务提交；审计不存密码、密码哈希、TOTP 密钥或验证码。部署时也必须禁止网关/APM/请求日志记录这些接口的请求体，原因字段中不要填写秘密。
- 二次验证失败计数独立事务提交，5 次失败封锁 15 分钟；TOTP 记录实际接受的时间计数器，成功后不能重放。即使后续业务写入失败，已使用的验证码也不能再次使用。
- 全局账号 authorization_version 加入权限缓存键，每次请求先校验账号有效性与版本；撤权不依赖“该用户加入过哪些租户”。版本变化影响后续请求，不会撤销已进入执行阶段的请求。
- 组织与成员启停存于 tenant_user_rel，权限上下文不再读取全局 User.orgId。成员停用不等于全局账号停用。成员移除不删除全局账号。

## 迁移与发布

运行时依赖：core-implementation 必须同时装载 tenant-implementation，以提供成员、组织和租户仓库。该依赖已在 Gradle 中声明为 runtimeOnly；授权服务使用同一权限实现时也需要它，不能只验证 common 的编译。

1. 备份数据库；先落实上一轮的数据权限迁移（20260908-role-scope-binding.sql）。
2. 在维护窗口检查：现有可用超级管理员至少一个；账号有效性字段无意外空值；tenant_user_rel 没有重复 tenant_id/user_id（包括软删除行）。
3. 执行同目录 sql/20260908-platform-accounts.sql。脚本为增量迁移，重复成员会中止整笔事务，需人工核对后再执行，不会自动删数据。
4. 旧 User.orgId 仅回填到组织所属的那个有效租户成员关系；无法匹配的记录保留旧字段，但不会再产生组织数据权限。上线前人工检查这些成员并补选正确组织。
5. 同步发布 common、authorization 及使用 security-core 授权解析器的服务；不要长时间混跑新旧权限消费者。发布新 common 远程前端，按项目现有 bootstrap 机制加载更新后的 common.json 和 i18n 贡献。不要仅复制页面文件。
6. 验证平台菜单、独立授权、旧接口拒绝、最后管理员保护、审计、撤权后请求拒绝，以及两租户成员组织隔离。浏览器重新加载，必要时重新登录刷新工作台信息。

迁移不创建默认管理员、不会硬编码或授予任何具体账号权限。安全锁行缺失时平台写入失败关闭。若没有任何有效超级管理员，需走受控的启动引导/数据库应急恢复流程，由运维确认具体账号；不可通过普通用户接口自助提权。

不建议直接回滚旧程序：旧版本不识别成员停用、成员组织和全局身份版本。确需回退时先停止流量、备份新身份与审计数据，再制定兼容恢复方案；不要直接删新表或重新开放旧通用用户写接口。

## 验证范围

新增 H2 数据库集成测试覆盖真实 JPQL、身份持久化、最末管理员并发保护、审计与失败验证事务、TOTP 防重放、租户成员隔离；授权上下文/缓存和旧接口服务测试覆盖防提权。执行前端 typecheck、common 构建及 i18n 检查。

这些测试不替代 PostgreSQL 迁移演练和浏览器端到端验收。部署时应保留数据库备份和单独的验收记录；部署不会自动分配真实账号的平台身份。
