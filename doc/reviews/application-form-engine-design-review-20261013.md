# 表单引擎架构评审

> 评审日期：2026-10-13\
> 评审范围：APP 表单控制面、DNA 物理模型与 Record Runtime、Workflow Center、平台 UI 契约\
> 结论：总体方向通过。第 1–6 节保留初次评审事实，后续实现进展见追加章节；当前完成度以权威实施计划为准，整体交付仍未完成。

## 1. 结论

当前设计的领域边界合理，可以继续沿用：

- APP 持有表单、页面、场景、规则、版本和发布编排。
- DNA 持有物理模型、Schema 演进、记录 CRUD、数据权限和目标数据库事务。
- Workflow 持有流程定义、实例、任务和历史事实。
- 浏览器只访问 APP 的设计态和运行态接口，不接收或提交物理模型、数据源、表名和任意 SQL。
- 表单版本拆分数据、界面和规则语义；业务记录仍进入每表单一张真实物理表。

这套边界能够支撑应用工作台、拖拽表单、多场景、真实表、标准 CRUD 和现有流程引擎。当前无需更换总体架构，也不应把 APP、DNA 和 Workflow 合并为一个服务。

当前实现还不能进入完整发布阶段。下面的问题会影响数据正确性、历史版本可重现性或组件扩展，必须先固化协议。

## 2. 已确认的合理设计

### 2.1 页面、表单和场景分离

应用页面是导航和授权入口，表单是稳定的数据与交互定义，场景是某个不可变表单版本中的渲染容器。一个字段可以在多个场景中出现，但只有一个数据定义。这个关系可以避免把页面 ID、表单 ID 和物理模型 ID 混为一体。

### 2.2 控制面与数据面分离

APP 不生成 DDL、不拼接业务 SQL，也不直接连接目标数据源。APP 只编译受控存储投影并调用 DNA 的结构化 API。DNA 根据受信元数据生成方言 DDL，通过 JDBC 在目标库执行；查询和标准 DML 经过 Calcite 规划和下推。

这里的统一边界应表述为“统一经过 DNA 数据平台”，不能表述为“所有语句均由 Calcite 执行”。Calcite 适合查询和标准 DML 的解析、校验、规划与下推；厂商 DDL 仍由 DNA 的 Schema Planner、方言适配器和 JDBC 执行。表单引擎调用结构化 Schema API，因此不会产生第二条 DDL 通道。

### 2.3 草稿、不可变版本和发布状态分离

可变草稿使用修订号防止静默覆盖，不可变版本用于发布和历史流程重现，发布记录承载跨服务幂等与恢复。目标库 DDL、DNA 控制库和 APP 控制库没有分布式事务，采用可恢复状态机是正确选择。

### 2.4 平台 UI 契约完整

标准资源列表使用 `SimpleTable` 和服务端 `/schema`，设计器内部树、差异和规则等复合数据使用 `DataTable` 或专用画布，标准表单和选择器复用 `SForm`、`EntitySelect` 及平台领域选择组件。该约束应继续作为合并门禁。

## 3. 阶段 2 前必须解决的问题

### 3.1 区分业务必填、存储非空和记录状态

评审时字段协议只有 `required`。设计同时要求业务记录支持 `SAVE_DRAFT`，如果 `required` 直接编译为数据库 `NOT NULL`，未填写完整的业务草稿无法保存；如果所有字段都可空，又会让设计者误以为数据库具有非空约束。

必须明确三个概念：

- `required`：某个运行动作或校验阶段的业务必填规则。
- `storageNullable` 或等价存储约束：任何记录状态都必须满足的物理约束。
- `recordState`：至少包含 `DRAFT`、`SUBMITTED`，由平台拥有，不能由普通字段覆盖。

第一版建议业务字段默认物理可空，`SUBMIT` 时执行完整服务端校验；只有具有安全默认值且草稿状态也能满足的字段才允许发布为物理非空。记录状态应进入 DNA 平台系统字段或另一种可随记录原子更新的受控字段，不能只放在浏览器或流程变量中。

### 3.2 历史表单版本不能与当前物理版本做简单相等校验

流程实例固定表单版本是正确的，但物理表会继续演进。如果表单版本 V1 绑定物理模型 V1，表结构后来安全演进到 V2，历史流程仍应使用 V1 的字段投影读取或办理记录。简单要求 `expectedModelVersion == activeModelVersion` 会让所有历史实例失效。

DNA Record 契约需要采用兼容性校验：

- APP 提交 `requestedSchemaVersion` 或不可变字段投影标识。
- DNA 验证该版本属于同一模型，且当前活动结构仍兼容其字段身份和类型。
- 读取和更新只允许访问该旧版本声明的字段集合。
- 破坏性迁移在存在受保护版本或活动流程时继续禁止。

历史渲染读取旧表单快照，物理执行仍使用当前活动表；稳定 `fieldId` 和不可复用身份负责兼容映射。

### 3.3 组件实例必须固定组件版本和受控属性

评审时 `FormComponentDescriptor` 已有版本，但 `FormComponentDefinition` 没有保存组件版本，也没有受控属性对象。固定的 `columnSpan`、`label`、`placeholder` 等字段不足以支持标签页、选择器、附件、动作配置和未来插件组件，也无法保证旧表单使用原来的组件语义。

组件协议需要补齐：

- 组件实例保存 `componentVersion`。
- 描述符提供属性 Schema、默认值、允许父子关系和迁移策略。
- 实例属性使用有大小、深度和键集合限制的 JSON 对象，并由对应版本描述符在服务端校验。
- 运行端按 `type + componentVersion` 解析，不自动用最新版解释历史快照。
- 扩展注册表采用组合式 SPI；重复类型和版本在启动时失败，不能用一个替换 Bean 静默覆盖平台内置组件。

### 3.4 checksum 必须基于规范化语义

评审时实现直接对 Jackson 输出做 SHA-256，只能保证同一对象序列化稳定，不能保证相同语义稳定。例如字段定义列表换序但场景布局不变时，checksum 会变化；引入属性 Map 后，键顺序也可能影响结果。

编译器应先生成规范化文档和独立的存储投影：

- 保留场景子节点顺序，因为它影响布局。
- 对字段、规则、非展示集合按稳定 ID 排序。
- 对对象属性递归按键排序。
- 统一数字、时间、空值和默认值表示。
- 分别计算 `documentChecksum` 与 `storageChecksum`。

UI-only 变更只有 `documentChecksum` 变化，不能创建新的 DNA 物理版本。

### 3.5 APP 与 DNA 的 Record 契约还缺两个正确性字段

当前 DNA `RecordCreateCommand`、`RecordUpdateCommand` 和 `RecordDeleteCommand` 接收物理模型 ID，但尚未提供计划要求的模型版本兼容标识；新增命令也没有幂等键。APP 在网络重试或流程启动恢复时可能重复插入记录。

进入表单运行时前必须补齐：

- 新增和原子命令组支持租户范围幂等键及持久化结果重放。
- 记录命令携带请求的 Schema 版本或投影标识，并执行 3.2 的兼容校验。
- APP 对浏览器隐藏物理模型 ID，将 `fieldId` 转换为 DNA 的稳定字段身份或存储代码。
- DNA 的通用治理接口保持现状；APP 使用窄范围服务间适配器，不能把治理 Controller 直接暴露为表单运行接口。

### 3.6 存储投影需要索引和唯一约束

当前表单字段协议不足以表达正式测试数据要求中的唯一约束、组合索引和业务查询索引。应在 `dataSchema` 中增加稳定 ID 的索引定义，引用 `fieldId`，由编译器转换为 DNA `LogicalIndexDefinition`。普通设计器只开放安全的唯一/普通索引能力，高级表达式索引不进入第一版。

### 3.7 发布状态和资源可见性必须一致

发布状态图包含旧版本 `RETIRED`，当前 APP 发布状态枚举尚未包含该状态。页面资源绑定也必须先以不可运行状态准备，APP 活动版本切换后才对运行路由可见，避免“资源已注册但表单未激活”的窗口。

发布协议需要满足：

- 同一表单同一版本只有一条发布聚合，重试递增 attempt，不重复创建。
- 新版本激活时，旧活动发布记录进入 `RETIRED`。
- 页面绑定由稳定绑定记录解析，运行接口只接受 `ACTIVE` 绑定。
- DNA 已准备而 APP 激活失败时保留准备版本并允许重试，不执行虚假回滚。
- 回退到旧表单版本前执行当前物理结构兼容检查。

### 3.8 数据库租户关系需要约束级防护

当前控制面表都带 `tenant_id`，但外键只引用单列 ID。服务层已有租户检查，数据库仍应防止错误代码写入“子表租户与父表租户不一致”的记录。

正式迁移应使用租户组合唯一键和组合外键，或通过等价的数据库约束保证：

- 表单租户与应用租户一致。
- 草稿、版本、发布租户与表单租户一致。

服务端租户校验继续保留，数据库约束作为第二道完整性边界。

## 4. 进入完整产品前的容量与运维约束

每租户每表单一张物理表会带来可预期的表数量增长。当前每应用 100 表单上限不足以控制整个租户和共享 Schema 的总表数。发布前需要增加：

- 应用级服务端存储配置，只保存逻辑 `storageProfileKey`，第一次发布后禁止普通用户切换。
- 每租户活动物理模型数、每数据源表数、每表字段数和索引数配额。
- 物理命名冲突、数据库标识符长度和保留字测试。
- 归档只停止写入和隐藏入口，物理 DROP/TRUNCATE 进入独立治理生命周期。

跨数据源写入、分片和批量导入仍属于后续能力，不阻塞基础闭环；基础闭环的所有命令应保留幂等键、批次标识和逻辑放置键，避免未来新增旁路。

- 文档 checksum 已规范化非展示集合顺序；存储投影编译器会规范化默认值并产生独立 storage checksum。
- 表单版本表已保存 DNA 存储投影 JSON、storage checksum 和待发布绑定的物理模型版本。

阶段 2 后续实现进展（2026-10-13）：

- 3.2 的历史 Schema 引用、checksum 所属校验、兼容性判断和稳定字段身份映射已经进入 DNA Record Runtime。
- 3.5 的 APP-DNA 窄范围远程契约和受限授权上下文传播已经实现，调用结束会恢复原上下文。DNA 对远程调用方采用显式服务白名单并默认拒绝，避免其他服务伪造租户或管理员上下文。
- 单条新增幂等已经实现为控制库持久化回执、请求指纹和服务端确定性记录 ID。该设计能够恢复“目标数据源已提交、服务响应丢失”的不确定结果；同键不同负载会稳定冲突。
- 原子命令组尚未具备组级幂等回执，不能把单条新增的保证扩大解释为批量事务保证；该项继续作为阶段 2 阻塞项。
- 新增回执表使用 `(tenant_id, physical_model_id, idempotency_key)` 唯一约束及租户组合外键，PostgreSQL 17 已验证迁移可重复执行、状态约束和错租户拒绝。
- APP 已有 DNA Schema 准备协调器：只自动执行 `SAFE` 计划，注册、版本创建和发布响应丢失后分别按表单归属、最新 checksum、模型与目标版本恢复。DNA 远程契约新增按模型与目标版本查询迁移记录，首次发布超时后不再依赖未知的 `migrationId`。

## 9. 后续运行协议与设计器入口收口

## 29. 发布取消的目标确认进展（2026-10-14）

## 32. 真实部署验证发现的问题（2026-10-14）

- 新发布已强制串接影响编译、目标策略检查、持久化反馈与授权修复入口；保存时继续校验其他活动页面的要求。该机制不能被描述为已经完成独立业务约束模型或 Workflow 集成。

- 真实验收使用非所有者的租户管理员账号。发布权限不代表运行数据权限，未授予动态资源时应拒绝访问。测试通过既有角色资源增量接口，仅授予测试页面资源，再验证实际记录能力。
